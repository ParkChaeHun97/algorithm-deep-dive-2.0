### 1. BOJ 1717 - 집합의 표현

**문제**
n+1개의 원소로 이루어진 집합에 대해 합집합(union) 연산과 두 원소가 같은 집합인지 확인(find) 연산을 처리하는 자료구조를 구현하는 문제. n은 최대 100만, 연산은 최대 10만 개.

**접근**
- `parent[]` 배열로 각 원소의 부모를 관리, 초기값은 자기 자신
- `find(a)`: 재귀로 루트까지 올라가며 `parent[a] = find(parent[a])`로 경로 압축(path compression) 동시 수행
- `union(a, b)`: 먼저 `a`, `b`를 각각 `find()`로 루트로 바꾼 뒤, `parent[a] = b`로 연결

**실수**
- `union`에서 `parent[a] = parent[b]`로 잘못 시도할 뻔함 — 이는 "a와 b를 같은 부모의 형제로 만드는" 것이지 "a를 b 밑에 합치는" 게 아님. `find()`로 이미 루트로 바꾼 뒤 `parent[a] = b`를 해야 두 집합이 정확히 합쳐진다는 걸 확인함

**토론한 내용**
- `find()`를 재귀 대신 반복문(while)으로도 구현할 수 있다는 것을 확인함 — 재귀는 코드가 짧지만 극단적인 경우 스택 오버플로우 위험이 있고, 반복문은 스택을 안 써서 대용량 데이터에 더 안전함. 이번 문제는 경로 압축 덕분에 재귀로도 문제없이 통과 가능

### 3. BOJ 1197 - 최소 스패닝 트리 (MST, 크루스칼)

**문제**
그래프가 주어졌을 때 모든 정점을 연결하는 부분 그래프 중 가중치 합이 최소인 트리(MST)의 가중치를 구하는 문제. 정점 최대 10,000개, 간선 최대 100,000개.

**접근 (크루스칼 알고리즘)**
- 모든 간선을 가중치 오름차순으로 정렬
- 정렬된 순서대로 간선을 확인하며, 두 정점이 이미 같은 집합(사이클 발생)이면 스킵, 다른 집합이면 union하고 가중치 누적
- 이번 문제부터 객체지향 설계를 의식적으로 시도함: `Graph`(간선 데이터 보관), `UnionFind`(parent 배열을 파라미터로 받는 순수 static 유틸), `MST`(Graph를 조합해 크루스칼 로직을 실행) 세 클래스로 분리

**실수**
- 간선을 읽는 반복문을 `for (int i = 1; i < E; i++)`로 짜서 간선 하나를 통째로 못 읽음 — `i = 0`부터 시작하도록 수정
- `Graph`의 간선 배열 크기를 `V+1`(정점 개수 기준)로 잘못 잡음 — 간선 배열은 정점 개수가 아니라 간선 개수(E) 기준으로 잡아야 함. 생성자에 E를 추가로 받아 `new int[E][3]`로 수정
- `setWeight()`에서 두 정점이 다른 집합일 때 가중치만 더하고 `union()` 호출을 빠뜨림 — union을 안 하면 두 정점이 계속 다른 집합으로 남아있어 사이클 판별이 전혀 작동하지 않고 사실상 모든 간선의 가중치를 다 더하게 됨. `union()` 호출 추가로 해결

**토론한 내용**
- `List<int[]>` 대신 `int[][]`(2차원 배열)을 선택한 이유를 짚음 — 간선 개수(E)를 입력에서 미리 알 수 있어 크기 가변이 필요 없고, `Arrays.sort()`에 Comparator를 바로 넘겨 정렬 가능하며 오토박싱 오버헤드도 없음
- 오늘 처음으로 객체지향 설계를 의식적으로 적용해본 것에 대해 리뷰함:
    - 잘된 점: `Graph`/`UnionFind`/`MST`로 책임이 명확히 나뉨, `UnionFind`를 parent 배열을 인자로 받는 순수 유틸로 분리해 다른 문제에도 재사용 가능하게 만든 점
    - 아쉬운 점 1: `main`에서 `mst.getGraph().addArray(...)`처럼 `MST` 내부의 `Graph` 객체에 직접 접근함 — 디미터 법칙 위반. `MST`에 `addEdge(...)` 같은 창구를 만들어 내부 객체를 감춰야 함
    - 아쉬운 점 2: `main`이 `parentInit() → sortGraph() → setWeight()`를 정확한 순서로 직접 호출해야 하는 부담을 짐 — `MST` 내부에 `run()` 메서드를 만들어 순서를 캡슐화하면, 외부는 순서를 몰라도 되고 실수 여지도 사라짐
    - 두 지적 모두 "내부 구조/내부 실행 순서를 외부에 노출하지 말고 캡슐화하라"는 동일한 원칙으로 귀결된다는 것을 사용자가 스스로 정리함

## 회고
- 1717에서 union 방향(`parent[a]=b` vs `parent[a]=parent[b]`)을 헷갈렸지만, "find()로 이미 루트로 치환된 상태"라는 조건을 이해하고 나니 바로 정리됨 — 유니온파인드는 코드 자체보다 "언제 find를 거쳤는지"를 놓치면 헷갈리기 쉽다는 걸 체감함
- 1197에서 겪은 세 가지 버그(반복문 시작 인덱스, 배열 크기 기준 착각, union 호출 누락) 모두 로직 설계보다는 "구현 단계의 사소한 누락"에 가까웠음 — 다익스트라 복습(1753) 때와 비슷하게, 알고리즘 뼈대 자체는 빠르게 복구됐고 디테일에서 시간이 걸림
- 처음으로 코드를 짜기 전부터 객체지향 설계(Graph/UnionFind/MST 분리)를 의식적으로 적용해봄 — Day4에서 다룬 SRP 개념을 하루 만에 실전에 적용한 것. 이후 리뷰에서 나온 "디미터 법칙"과 "실행 순서 캡슐화(run 메서드)" 두 지적을 스스로 "내부 접근 금지"와 "메인은 실행만 알면 됨"으로 정확히 요약함
- 1976(여행가자)은 난이도가 낮다고 판단해 스스로 스킵 결정 — 학습 우선순위를 스스로 조정하는 판단이 이루어짐
