## 카카오 2020 - 키패드 누르기 (Lv1)

### 문제
5x3 휴대폰 키패드에서 왼손은 '*', 오른손은 '#'에서 시작. 1,4,7은 왼손, 3,6,9는 오른손
고정, 2,5,8,0은 두 엄지 중 현재 위치에서 더 가까운 손으로 누름(상하좌우 이동 기준,
대각선 불가). 거리가 같으면 hand(오른손잡이/왼손잡이)로 결정. 각 숫자를 누른 손을
"L"/"R"로 표시한 문자열을 반환하는 문제.

### 접근
- 키패드를 4x3 좌표로 매핑 (1~9는 0~2행, *,0,#은 3행)
- 1,4,7 / 3,6,9는 항상 고정된 손이므로 switch로 즉시 처리
- 2,5,8,0은 현재 왼손/오른손 좌표에서 목표 좌표까지의 최단거리를 구해 비교
- 거리 계산을 처음엔 BFS로 구현했으나, 이 키패드에는 장애물이 없어 상하좌우 이동만으로
  최단거리가 항상 "행 차이 + 열 차이"(맨해튼 거리)와 같음 → 그래프 탐색 없이
  Math.abs(dx)+Math.abs(dy)로 대체 가능하다는 것을 확인함 (이번엔 시간 문제로 BFS 버전을
  그대로 완성해서 제출, 리팩토링은 추후 과제로 남김)

### 실수
- **case 2에서 break 누락**: switch문의 case 2 블록 끝에 break가 없어서, 2를 처리한 뒤
  바로 이어서 case 5 로직까지 실행되어버리는 문제 발생 (15649 때 겪었던 return 누락과
  같은 유형의 실수가 switch문에서 재발함) → break 추가로 해결
- **문자열 비교에 == 사용**: `hand == "left"`처�럼 문자열을 참조 비교 연산자로 비교함
  → `hand.equals("left")`로 수정
- **case 8, 0의 손 위치 갱신 좌표 오류**: 8의 목표 좌표는 {2,1}인데 갱신 시 {1,2}로,
  0의 목표 좌표는 {3,1}인데 갱신 시 {1,3}으로 행/열이 뒤바뀌어 있었음 → 목표 좌표와
  동일하게 수정
- **case 2의 목표 좌표 자체가 틀림**: bfs 호출 시 목표를 {1,0}(4번 좌표)으로 잘못 주고,
  갱신은 {0,1}(2번의 실제 좌표)로 하는 불일치가 있었음 → bfs 호출의 목표도 {0,1}로 수정
- 이 문제를 해결하는 데 1시간 30분이 걸렸는데, 원인은 알고리즘 이해 부족이 아니라
  좌표를 손으로 하나하나 옮겨적는 과정에서 발생한 반복적인 오타/불일치였음

## 회고
- Lv1 문제였지만 좌표 매핑이 많은 문제 특성상 사소한 오타가 누적되어 시간이 오래 걸림.
  알고리즘 설계(가까운 손 판단, 거리 비교) 자체는 처음부터 올바른 방향이었음
- switch문에서도 for문/재귀와 마찬가지로 break 누락이 실수로 이어질 수 있다는 것을 확인함
- 문제 상황에 맞는 도구를 고르는 것의 중요성을 체감함: 장애물 없는 격자의 최단거리는
  BFS 없이 좌표 차이만으로 계산 가능하다는 것을 알게 됨 (다음에 비슷한 유형을 만나면
  더 간단한 방법을 먼저 검토할 것)
