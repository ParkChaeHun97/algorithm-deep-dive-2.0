## 합승 택시 요금 (2021 KAKAO 채용연계형 인턴십)

### 문제
지점 s에서 출발해 지점 a와 b로 가는 두 사람이 있을 때, 택시를 같이 타다가 어느 지점에서 갈라져서 각자 목적지로 가는 방식으로 최소 총 요금을 구하는 문제. n(최대 200)개의 지점, 양방향 가중치 그래프. 처음 접하는 유형이라 플로이드-워셜 개념부터 전날 미리 정리하고 들어감.

### 접근
- **핵심 아이디어**: 갈라지는 지점 p를 s, a, b로 고정하지 않고 **모든 노드(1~n)를 후보로 순회**해야 함. `answer = min(1≤p≤n) [dist[s][p] + dist[p][a] + dist[p][b]]` — p=s면 "따로 감", p=a/b면 "한쪽 목적지까지 같이 간 뒤 갈라짐"에 해당하며, 이 식 하나가 모든 경우를 포함함
- **플로이드-워셜**로 먼저 모든 노드 쌍 최단거리(`dist[i][j]`)를 구함 — 삼중 for문(k 바깥, i, j 안쪽), `dist[i][j] = min(dist[i][j], dist[i][k]+dist[k][j])`
- 이후 단일 for문으로 p(1~n)를 순회하며 `dist[s][p]+dist[p][a]+dist[p][b]`의 최솟값을 구함 (플로이드-워셜은 한 번만 수행, 이후는 배열 조회만)

### 실수
1. **`Graph` 생성자에서 대각선(`arr[i][i]`)을 0으로 안 잡음** — `Arrays.fill(arr[i], INF)`로 채우면 자기 자신까지 INF가 되어버림. 플로이드-워셜의 전제(자기 자신 거리=0)가 깨져서, p=s인 경우(따로 타고 가는 경우) 등에서 계산이 틀어짐. 생성자에서 `arr[i][i]=0`을 별도로 설정해 해결
2. **`addEdge`를 단방향으로만 저장** — `arr[a][b]=weight`만 하고 `arr[b][a]=weight`를 빠뜨림. 이 문제의 그래프는 양방향인데 한쪽만 저장되어 절반의 경로가 아예 존재하지 않는 것처럼 계산됨
3. **INF(무한대 대체값) 크기를 세 차례에 걸쳐 잘못 설정 — int 오버플로우 문제**:
    - 1차 시도: `INF = Integer.MAX_VALUE` → 플로이드-워셜 갱신식(`arr[i][k]+arr[k][j]`)에서 두 INF를 더하면 int 범위(약 21억)를 넘어 오버플로우, 결과가 음수(쓰레기값)로 나와 최단거리보다 작다고 잘못 판단됨
    - 2차 시도: `INF = 1,000,000` (100만) → 이번엔 반대로 너무 작음. 문제 제약상 실제 최단거리가 n×최대가중치(200×100,000=2천만)까지 나올 수 있는데, INF(100만)가 그보다 작아서 "진짜로 안 이어진 노드"를 "가짜로 이어진 것"처럼 오판
    - 3차 시도: `INF = 1,000,000,000` (10억) → 플로이드-워셜 갱신식(두 항 덧셈)은 안전해졌지만, `returnResult`에서 **세 항**(`dist[s][p]+dist[p][a]+dist[p][b]`)을 더할 때 최악의 경우 10억×3=30억이 되어 다시 오버플로우 발생 (고립된 컴포넌트가 있는 테스트케이스에서 `-1294967296` 같은 값으로 드러남)
    - 최종 수정: `INF = 200,000,000` (2억)으로 낮춤 — 실제 최대 거리(2천만)보다 충분히 크면서, 세 번 더해도(6억) int 범위 안에 안전하게 들어옴

### 토론한 내용
- 플로이드-워셜 개념을 전날 미리 정리: 다익스트라(한 정점→모든 정점)와 달리 모든 정점 쌍 최단거리를 한 번에 구한다는 것, "정점 k를 경유하면 더 빠른가"를 모든 k에 대해 순서대로 확인한다는 직관을 손으로 예제(1→3→2 경유)를 계산하며 확인
- "다익스트라를 n번 반복하면 안 되냐"는 질문에 대해, n=200 기준으로 시간복잡도를 직접 비교(플로이드-워셜 O(n³)=800만 vs 다익스트라 n회 반복)해보고 둘 다 시간 안에 들어오지만, 이 문제 규모에서는 플로이드-워셜이 구현이 더 간결하다는 결론
- "왜 s/a/b뿐 아니라 임의의 노드 p까지 다 확인해야 하는가"를 반례(그래프 구조상 s,a,b와 각각 가까운 중간 노드 p가 있는 경우)로 직접 검증하며 이해함
- "무한대를 정수로 흉내 낼 때, 이 값이 코드 안에서 최대 몇 번 더해지는지"까지 계산해서 크기를 정해야 한다는 원칙을 이번 문제에서 실전으로 체득함 — 두 번 더하는 곳(플로이드-워셜 갱신식)과 세 번 더하는 곳(최종 p 순회)의 안전 기준이 서로 다르다는 것을 직접 겪으며 확인

## 회고
- INF 값 하나를 놓고 세 번이나 다시 조정해야 했음 — "적당히 큰 값"이라는 감으로 설정했다가 오버플로우를 반복해서 겪은 뒤에야 "코드 전체에서 이 값이 몇 번까지 더해질 수 있는가"를 역산해서 정확한 상한을 구하는 방식으로 전환함. 이번 주 내내 강조된 "경계값/한계값을 미리 계산해서 확인하기" 원칙이 여기서는 무한대 값 설정이라는 새로운 형태로 나타남
- 그래프 초기화 시 "대각선(자기 자신)" 처리와 "양방향 저장" 두 가지는, 지난 주 유니온파인드/MST 때는 문제되지 않았던 부분이라 새로 마주친 실수 유형이었음 — 플로이드-워셜처럼 "그래프 전체 구조를 한 번에 다루는" 알고리즘에서는 이런 기본 초기화 누락이 결과 전체를 흔든다는 걸 체감함
- 전날 개념(플로이드-워셜, "임의의 p가 답일 수 있다")을 미리 정리하고 들어간 덕분에, 실제 구현 단계에서는 알고리즘 설계 자체보다 오버플로우/초기화 같은 구현 디테일에서만 시간이 걸렸음 — 개념을 미리 다지고 들어가는 것의 효과를 확인함
