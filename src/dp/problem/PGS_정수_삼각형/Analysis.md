## 정수 삼각형 (프로그래머스 Lv3)

### 문제
삼각형 모양으로 숫자가 배치되어 있을 때, 맨 위 꼭짓점에서 시작해 아래로 내려가며(왼쪽 아래 또는 오른쪽 아래로만 이동) 마지막 줄까지 도달했을 때, 지나간 숫자의 합이 최대가 되는 경로의 합을 구하는 문제. 2차원 DP로 접근해야 함.

### 접근
- `dp[i][j]`를 (n+1)×(n+1) 크기로 잡고 **1-indexed**로 관리, `triangle`은 0-indexed이므로 참조할 때만 `triangle[i-1][j-1]` 규칙으로 변환
- 초기값: `dp[1][1] = triangle[0][0]`, n==1이면 조기 리턴
- `dp[2][1]`, `dp[2][2]`는 루프 밖에서 별도로 초기화
- i=3부터 n까지, j=1부터 i-1까지 순회하며 "위에서 아래로 값을 흘려보내는" 방식으로 갱신:
```java
  dp[i][j] = max(dp[i][j], dp[i-1][j] + triangle[i-1][j-1]);   // 왼쪽 부모에서 내려옴
  dp[i][j+1] = dp[i-1][j] + triangle[i-1][j];                   // 같은 부모가 오른쪽 자식에도 기여
```
같은 `dp[i-1][j]`가 자기 자신과 오른쪽 칸(`j+1`) 양쪽에 값을 전달하는 구조. `dp[i][j+1]`은 먼저 `=`로 채워지고, 다음 반복(`j+1`)에서 `dp[i][j]`가 `max`로 갱신될 때 다시 참조되므로 순서상 값이 씹히지 않음
- 마지막 줄(`dp[n][1..n]`) 중 최댓값을 출력

### 실수
- 없음 — 처음부터 정확하게 구현함. 다만 **인덱스를 맞추는 과정 자체에서 시간이 많이 걸림** (triangle과 dp 사이의 오프셋, i-1/j-1 규칙을 헷갈리며 여러 번 고침)

### 토론한 내용
- 코드 로직이 일반적인 "아래 칸이 위쪽 두 부모 중 큰 값을 선택"하는 방식이 아니라, "위 칸이 아래 두 자식에게 값을 흘려보내는" 반대 방향 구조였다는 점을 직접 손으로 트레이스(row2~row5)하며 확인함 — 예제 입력으로 최종값 30이 정확히 나오는 것까지 검증
- **인덱스 삽질을 줄이는 방법**에 대해 논의함:
    - dp 배열을 1-indexed로 통일하고, triangle 참조 시에만 `-1` 규칙을 일관되게 적용하는 것
    - 코드를 짜기 전에 작은 삼각형(n=2~3)을 좌표(`(i,j)`)와 화살표로 직접 그려보고 시작하는 것
    - "행의 원소 개수 = 행 번호"라는 삼각형의 특성을 인덱스 범위 검산 기준으로 활용하는 것
    - `Arrays.deepToString(dp)`처럼 배열 전체를 찍어서 눈으로 확인하는 방법
- **IDE 디버거 없는 실전 코테 환경**에서의 대안도 논의함:
    - `println`은 코테 환경에서도 자유롭게 쓸 수 있으므로, 배열 상태를 찍어보는 습관은 그대로 유효함
    - 헬퍼 함수 단위로 로직을 쪼개서 부분적으로 검증하는 방식 (파일명 정렬의 `splitHNT()`처럼)
    - 가장 본질적인 건 "본인이 반복적으로 틀리는 지점"을 analysis.md 등에 누적해서, 코드 짤 때 그 지점에서 한 번 더 스스로 점검하는 습관을 들이는 것

## 회고
- 2차원 DP로의 전환(1차원 dp[i] → 2차원 dp[i][j])이 오늘 처음이었는데, 로직 설계 자체는 계단 오르기에서 연습한 "여러 상태로 나누기" 감각이 그대로 적용돼서 큰 어려움 없이 됨
- 반면 로직보다 **인덱스 매핑(0-indexed triangle ↔ 1-indexed dp)**에서 시간을 더 많이 씀 — 다음 2차원 DP 문제부터는 코드 짜기 전에 좌표를 직접 그려보는 걸 먼저 시도해보기로 함
- "IDE 디버거 없이 어떻게 검증하나"라는 실전 코테에 대한 고민이 나왔고, 결국 오늘 계속 해온 손트레이스 습관이 디버거의 대체 수단이라는 것으로 정리됨
