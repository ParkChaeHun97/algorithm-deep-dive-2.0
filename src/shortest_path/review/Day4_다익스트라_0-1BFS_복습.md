## Day4 - 다익스트라 / 0-1 BFS 복습 (최단경로 / 알고스팟)

---

### 1. BOJ 1753 - 최단경로

**문제**
방향그래프에서 시작점 K로부터 다른 모든 정점까지의 최단경로를 구하는 문제. 정점 최대 20,000개, 간선 최대 300,000개, 간선 가중치는 10 이하 자연수. 여러 정점 사이에 중복 간선이 존재할 수 있음.

**접근**
- 인접 리스트(`List<List<int[]>>`)로 그래프 구성
- `PriorityQueue`로 현재까지 거리가 가장 짧은 정점을 먼저 꺼내는 정석 다익스트라
- `dist[]`를 `Integer.MAX_VALUE`로 초기화, 시작점만 0
- 큐에서 꺼낸 값이 이미 기록된 `dist`보다 크면(stale) 스킵
- 완화(relaxation) 조건으로 `dist[next] > dist[node] + weight`일 때만 갱신 후 큐에 삽입

**실수**
- 출력 시 `StringBuilder`에 이미 각 줄마다 `\n`을 붙여놓고 `System.out.println(sb)`을 호출해 맨 끝에 불필요한 빈 줄이 추가됨 → `System.out.print(sb)`로 수정
- (객체지향 리팩터링 과정에서) `BufferedReader`를 `input()`과 `Graph.addEdge()` 양쪽에서 각각 새로 생성함 — `System.in`을 감싸는 스트림은 프로그램 전체에서 하나만 존재해야 하는데, 두 개를 만들면 입력이 꼬여버림. `br`을 정적 필드로 하나만 두고 공유하도록 수정

**토론한 내용**
- 클래스 설계를 객체지향적으로 개선하는 방향에 대해 논의함: `Graph`(데이터 구조)와 `Dijkstra`(알고리즘)를 분리하는 것이 단일 책임 원칙(SRP)과 개방-폐쇄 원칙(OCP) 관점에서 더 적절하다는 것, `int[]{to, weight}` 같은 의미 없는 배열 대신 `Edge(int to, int weight)` record로 표현하면 가독성이 오른다는 것을 확인함
- 다만 코딩테스트 상황에서는 이 정도까지 분리하는 게 시간 대비 효율이 낮다는 점, 실무 설계 감각은 별도로 연습할 필요가 있다는 점으로 정리하고 실제 리팩터링은 보류함
- DP(계단오르기/LIS/연속합) 때와 달리 다익스트라는 표준 알고리즘의 뼈대(우선순위 큐, 완화 조건, stale 스킵)가 이미 체화되어 있어 복구가 훨씬 빨랐다는 차이를 짚음

### 2. BOJ 1261 - 알고스팟

**문제**
N×M 격자에서 (1,1)에서 (N,M)까지 이동할 때, 벽(1)을 부수면 비용 1, 빈 방(0)으로 이동하면 비용 0으로 보고, 최소 비용(=최소로 부숴야 하는 벽의 개수)을 구하는 문제. 0-1 BFS(덱을 이용한 다익스트라 대체)의 정석 문제.

**접근**
- `dy[]`, `dx[]`로 방향 벡터 관리, 격자는 `map[row][col]`로 관리하고 row=y(세로), col=x(가로)로 대응시킴
- 덱(Deque) 기반 0-1 BFS: 비용 0인 이동은 `offerFirst`, 비용 1인 이동은 `offerLast`
- `dist[][]`를 별도로 두어 원본 `map`(벽 정보 0/1)과 분리, `dist`는 `Integer.MAX_VALUE`로 초기화 후 시작점만 0
- 최단거리 갱신 조건(`newDist < dist[ny][nx]`일 때만 갱신 후 큐 삽입)을 다익스트라와 동일하게 적용
- 도착점 도달 시 조기 리턴하지 않고, 전체 탐색이 끝난 뒤 `dist[N-1][M-1]`을 반환

**실수**
- 처음에 내가(어시스턴트가) 예제 입력/출력을 잘못 만들어서 제시함 — 사용자가 손으로 경로를 따라가 "벽 없이도 도착 가능한데 왜 답이 3이냐"고 반례를 지적해 오류를 발견, 이후 실제 백준 원문 예제로 정정함
- **`visited` 배열로 한 번 방문한 칸을 완전히 차단**하는 방식으로 처음 접근함 — 일반 BFS(가중치 동일)에서는 "먼저 방문 = 최단"이 보장되지만, 0-1 BFS는 비용이 다르기 때문에 먼저 방문했다고 최단경로라는 보장이 없음. 이 상태로는 더 짧은 경로로 재방문할 기회 자체가 차단됨
- **원본 `map` 배열에 누적 거리를 직접 더해 덮어씀**(`map[ny][nx] += map[cy][cx]`) — 벽 정보(이동 비용 판단 기준)가 훼손되어 이후 경로 계산의 기준이 틀어짐. `map`(원본 정보)과 `dist`(누적 거리)를 분리해야 함
- `dist` 배열을 전부 **0으로 초기화**함 — 아직 도달 못 한 곳도 0이 되어버려 "더 큰 값이면 스킵" 조건에서 대부분의 탐색이 막혀버림. `Integer.MAX_VALUE`로 초기화하고 시작점만 명시적으로 0으로 설정하도록 수정
- 갱신 조건을 `newDist > dist[ny][nx]) continue`(초과일 때만 스킵, 같을 때도 갱신)로 짬 — 오답까지는 아니지만 같은 최단거리에 대해 불필요하게 재삽입되는 비효율이 있음. `newDist < dist[ny][nx]`(더 작을 때만 갱신)로 바꾸는 것이 관례적으로 더 적절함을 확인

**토론한 내용**
- "왜 visited만으로는 안 되는가"에 대해 반례(2×2 격자)로 직접 설명하고, 사용자가 "뒤에 넣는 게 비용 1인지 2인지 3인지 거리 보장이 안 된다"는 말로 핵심을 스스로 정리함
- 0-1 BFS가 결국 "다익스트라를 덱으로 구현한 특수 케이스"라는 점, 그래서 다익스트라의 핵심 원칙(방문 여부가 아니라 기록된 거리와의 대소 비교로 갱신 여부 판단)이 그대로 적용된다는 것을 확인함

## 회고
- 1753(다익스트라)은 표준 알고리즘 뼈대가 이미 체화돼 있어 복구가 빨랐던 반면, 1261(0-1 BFS)에서는 "방문 처리"에 대한 잘못된 직관(일반 BFS의 습관)이 남아있어 같은 실수 패턴(먼저 방문 = 최단이라는 가정)을 다시 겪음 — 알고리즘이 바뀌면 겉보기엔 비슷해 보여도 핵심 불변식이 다를 수 있다는 걸 체감함
- `map`(원본 데이터)과 `dist`(계산 결과)를 분리하지 않고 원본 배열에 직접 값을 누적하는 실수는, 정수 삼각형 문제 때와는 다른 유형의 "상태 오염" 버그였음 — 원본 입력 데이터는 절대 직접 변경하지 않고 별도 배열에 결과를 쌓는 습관을 다시 확인함
- 예제 자체가 잘못 주어졌을 때 스스로 손으로 경로를 따라가 모순을 발견해낸 것 — 주어진 예제나 힌트를 그대로 믿지 않고 직접 검증하는 태도가 유효했음
- 오늘 추가로 "객체지향적으로 잘 짰는지" 스스로 궁금해하며 SRP/OCP 같은 설계 원칙까지 짚어봄 — 코테 코드와 실무 설계는 목적이 다르다는 것으로 정리하고, 지금 단계에서는 코테 정확성에 집중하되 감각은 별도로 익혀두기로 함
