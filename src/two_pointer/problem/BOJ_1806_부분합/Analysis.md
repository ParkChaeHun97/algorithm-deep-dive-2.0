## BOJ_1806 - 부분합

### 문제
- N개의 수로 이루어진 수열에서, 합이 S 이상이 되는 부분 연속 수열 중 **최소 길이**를 구하는 문제
- 그런 부분 수열이 없으면 0 출력

### 접근
- 투 포인터(슬라이딩 윈도우) 사용
- `right`를 늘리며 sum을 키우다가, `sum >= S`가 되면 `left`를 좁히면서 최소 길이를 갱신
- O(N) — left, right 각각 최대 N번만 이동

### 헷갈렸던 지점
1. **문제 조건 오독**: "S 이상"인데 처음엔 다른 조건으로 잘못 이해하고 로직을 짬. 종료 조건이 완전히 어긋난 채로 시작해서, 정상적인 입력에도 0만 출력되는 상황이 발생.
2. **`sum == S`로 결과를 갱신하는 실수**: S를 딱 맞춰 지나가는 순간만 체크하니, 배열에 큰 값(예: 100)이 있어서 sum이 한 번에 S를 훌쩍 넘어버리면 `sum == S`인 순간 자체가 존재하지 않음 → 정답을 못 찾는 버그로 이어짐. `sum >= S`로 바꿔야 함을 반례(`3 100 3`, S=10)로 확인.
3. **result 갱신 코드 누락**: sentinel 값을 `0` → `Integer.MAX_VALUE`로 개선하는 과정에서, 정작 `result = Math.min(result, len)` 갱신 로직 자체를 빼먹음. 컴파일은 되지만 항상 0만 출력되는 조용한 버그였음 — 리팩토링할 때 핵심 로직이 딸려서 삭제되지 않았는지 항상 재확인해야 한다는 교훈.

### 코드 작성 중 발생했던 실수들
1. `sum == S` vs `sum >= S` 비교 조건 오선택
2. sentinel 값 리팩토링 중 result 갱신문 자체를 통째로 누락
3. (근본 원인) 문제 조건 "이상"을 처음에 잘못 해석하고 시작

### 회고
- 슬라이딩 윈도우에서 "정확히 맞아떨어지는 순간"을 조건으로 잡으면, 원소 값의 크기에 따라 그 순간이 아예 존재하지 않을 수 있다는 걸 체감함. 앞으로는 "조건을 만족하는 상태 전체"(`>=`)를 기준으로 잡는 습관을 들여야 함.
- 코드를 개선(리팩토링)할 때, 바뀌는 부분에만 집중하다가 원래 있던 핵심 로직을 실수로 지우는 경우가 생길 수 있음 → 수정 후엔 항상 반례로 재검증하는 습관이 중요.
