## 카카오 2022 - 성격 유형 검사하기

### 문제
4개 지표(R/T, C/F, J/M, A/N)에 대해 n개의 질문과 각 질문의 7개 선택지(매우비동의~매우동의)
점수를 바탕으로, 각 지표에서 더 높은 점수를 받은 유형을 조합한 4글자 문자열을 반환하는 문제.
동점이면 사전순으로 빠른 유형 채택. survey[i]는 "비동의 쪽 유형 + 동의 쪽 유형" 순서인데,
이 순서가 질문마다 뒤바뀔 수 있음(예: "MJ"와 "JM" 둘 다 존재 가능)이 핵심 함정.

### 접근
- `score[4][2]` 2차원 배열로 [지표][유형(왼쪽/오른쪽)] 점수를 관리
- `choiceScore[]` 배열로 choices 값(1~7)을 실제 점수(0~3)로 매핑
- choices가 1~3(비동의 방향)이면 survey의 첫 글자, 5~7(동의 방향)이면 survey의 둘째 글자에
  점수를 더함. 4(모르겠음)는 continue로 스킵
- 각 문자가 어느 지표(y좌표)와 어느 방향(x좌표: 사전순 빠른 쪽/느린 쪽)에 해당하는지
  char 값 비교로 판별
- 동점 처리 시 `type[i][0] > type[i][1]`로 char 코드값을 비교해 사전순으로 빠른 쪽을 선택
  (이 문제의 type 배열은 항상 왼쪽이 사전순으로 빠른 문자로 고정되어 있어, 결과적으로
  단순히 type[i][0]을 선택하는 것과 동일하지만, char 비교 자체는 사전순 비교의 정확한
  구현임을 확인함)

### 실수
- **type 배열 오타**: 4번 지표를 `{'A', 'M'}`으로 잘못 선언함 — M은 이미 3번 지표(J/M)에서
  쓰인 문자이고, 4번 지표는 어피치형(A)/네오형(N)이어야 함. `{'A', 'N'}`으로 수정
- 이 실수를 제외하면 점수 누적 로직, choices 방향 판별, 동점 비교까지 설계와 구현이
  전부 정확했음. 알고리즘적 오류가 아니라 상수 값(문자) 하나를 잘못 적은 단순 오타였음

### 토론한 내용
- 동점 처리 시 `type[i][0] > type[i][1]`처럼 char를 직접 비교하는 것이 "우연히 맞는
  코드"인지 논의함. 결론적으로 이는 우연이 아니라 사전순 비교의 정확한 구현이며,
  다만 이 문제의 type 배열이 항상 왼쪽=사전순 빠른 문자로 고정되어 있어 단순히
  type[i][0]을 쓰는 것과 결과가 동일할 뿐이라는 것으로 정리함. char 비교 방식이
  더 일반적이고 안전한 접근이라는 점도 확인

## 회고
- 2022년 인턴십 1번 문제(Lv1)답게, 복잡한 알고리즘 없이 순수하게 "문제 조건을 정확히
  자료구조에 반영하는 능력"이 핵심이었음. survey 문자열의 좌우 순서가 질문마다 뒤바뀔 수
  있다는 함정을 미리 인지하고 설계에 반영한 것이 정확한 구현으로 이어짐
- 유일한 실수가 로직이 아닌 상수 오타였다는 점에서, 앞으로도 이런 유형(고정된 매핑 테이블을
  손으로 입력하는 경우)에서는 각 값을 한 번 더 문제 설명과 대조하는 습관이 필요함을 확인
- char 비교를 이용한 사전순 판별 로직에 대해 "왜 이게 맞는 방식인지"를 놓고 서로 논리를
  주고받으며 검증한 과정 자체가, 단순히 정답 여부를 확인하는 것 이상으로 코드의 정확한
  근거를 이해하는 데 도움이 됨
