## 백준 1717 - 집합의 표현

### 문제
초기에 {0},{1},...,{n} 이 n+1개의 집합으로 존재. `0 a b`는 a와 b가 속한 집합을 합치는
합집합 연산, `1 a b`는 a와 b가 같은 집합에 속하는지 확인하는 연산. 확인 연산 결과를
YES/NO로 출력. 전형적인 유니온 파인드(서로소 집합) 문제.

### 접근
- `parent[]` 배열로 각 원소의 부모(대표)를 관리
- `find(x)`: parent[x]==x면 자기 자신이 대표이므로 반환, 아니면 재귀로 부모를 타고 올라가며
  경로 압축(`parent[x] = find(parent[x])`)
- `union(a,b)`: find로 각각의 대표를 찾은 뒤, 다르면 한쪽 대표를 다른 쪽 밑에 붙임
- 입력이 많을 수 있어(m 최대 10만) StringBuilder로 결과를 모아 한 번에 출력

### 헷갈렸던 지점 / 실수
- `init()`에서 반복문 범위를 `for (int i = 1; i < n; i++)`로 잘못 설정함
    - 인덱스 0이 초기화 루프에서 빠짐 (Java 배열 기본값이 0이라 우연히 맞아떨어졌지만 의도한 코드는 아니었음)
    - 인덱스 n도 `i < n` 조건 때문에 초기화가 안 되어, `parent[n]`이 0으로 남아있는 진짜 버그 발생
    - 문제의 집합 범위가 {0}~{n}이므로 `for (int i = 0; i <= n; i++)`로 수정

## 회고
- 유니온 파인드 자체의 핵심 로직(find 재귀 + 경로 압축, union의 대표 비교)은 어제 개념만 보고도
  코드로 정확하게 옮길 수 있었음. 다익스트라/0-1 BFS에 비해 확실히 개념이 단순해서 수월하게 진행됨
- 이번 실수도 지난 며칠과 비슷한 패턴: 알고리즘 로직이 아니라 배열 초기화 범위(경계값) 설정에서
  발생. 문제가 다루는 원소 범위(0부터 n까지 포함)를 반복문 조건에 정확히 반영하는 습관이
  계속 강화되어야 할 부분으로 확인됨
