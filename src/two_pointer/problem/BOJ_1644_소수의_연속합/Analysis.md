## BOJ_1644 - 소수의 연속합

### 문제
- 자연수 N이 주어졌을 때, N을 **연속된 소수의 합**으로 나타낼 수 있는 경우의 수를 구하는 문제
- 연속되지 않은 소수 조합(7+13=20 등)이나 같은 소수 중복 사용은 인정 안 됨

### 접근
- **에라토스테네스의 체**로 N 이하의 소수를 모두 걸러냄 (`isComposite` 방식, 배열 기본값 `false`를 그대로 활용해 초기화 코드 절감)
- 리스트에 소수를 모은 뒤 **배열로 변환**(반복 접근이 많은 투포인터 구간이라 박싱/캐시 오버헤드를 피하기 위함)
- 소수 배열에 대해 투포인터 적용
    - `sum < n`이면 오른쪽 확장
    - `sum >= n`이면 (`sum == n`일 때 카운트) 왼쪽 축소
    - 어느 쪽도 아니면(= 확장할 여지도 없이 sum이 n 미만) 종료
- 소수는 항상 양수라 `sum`이 단조증가 → 1806과 달리 여기선 `==` 비교가 정답 로직의 핵심이 됨 (핵심 값을 그냥 지나칠 일이 없음)

### 헷갈렸던 지점
1. **에라토스테네스 체 최적화 근거 이해**: 바깥 루프를 `i*i <= n`까지만 도는 이유와, 안쪽 배수 제거 루프를 `i*i`부터 시작해도 되는 이유를 처음엔 혼동함. 전자는 "i가 √n을 넘으면 i가 최소 인수인 합성수가 없다"는 것, 후자는 "i보다 작은 배수들은 더 작은 소수 차례에서 이미 제거됐다"는 것으로 각각 다른 근거임을 확인.
2. **`Math.sqrt(n)` vs `i*i` 비교**: `Math.sqrt`는 부동소수점 오차로 완전제곱수 근처에서 경계값이 틀어질 수 있어, 정수 연산인 `i*i <= n` 방식이 더 안전하다는 점을 짚고 넘어감.
3. **N=1 예외처리 필요 여부**: 처음엔 `n==1`일 때 별도로 0을 출력하는 조기 return을 넣었으나, 실제로는 일반 로직(소수 리스트가 빈 배열이 되고 while 조건이 바로 false)만으로도 자연스럽게 0이 나옴을 트레이싱으로 확인 → 불필요한 분기 제거.
4. **리스트→배열 변환 이유**: `ArrayList<Integer>`는 박싱된 객체 접근 오버헤드와 캐시 미스가 있어, 반복 접근이 많은 투포인터 구간에서는 `int[]`로 변환 후 사용하는 것이 유리함을 재확인.

### 코드 작성 중 발생했던 실수들
1. (실수라기보다 설계 검토) `n==1` 특수 케이스를 별도 분기로 처리했다가, 일반 로직만으로 충분히 커버됨을 확인하고 제거
2. 에라토스테네스 체 최적화 조건(`i*i` 두 지점)의 근거를 정확히 구분하지 못하고 뭉뚱그려 이해했던 부분 교정

### 회고
- 1806에서는 "sum이 S를 훌쩍 넘어버릴 수 있어 `==` 비교가 위험하다"고 배웠는데, 이 문제에서는 반대로 `==` 비교가 정답 로직의 핵심이었음. 두 문제를 비교하며 "언제 `==`가 안전하고 언제 위험한지"는 값의 증가 패턴(소수처럼 항상 양수로 단조증가하는지 여부)에 달려있다는 걸 체감함 — 슬라이딩 윈도우에서 종료/카운트 조건을 잡을 때 값의 성질부터 먼저 따져야 한다는 원칙 확립.
- 예외처리를 습관적으로 먼저 넣기보다, 일반 로직이 해당 케이스를 자연스럽게 처리하는지 먼저 트레이싱해보고 불필요하면 제거하는 습관이 코드를 더 깔끔하게 만든다는 걸 다시 확인.
- 에라토스테네스 체의 두 최적화(바깥 루프 범위, 안쪽 루프 시작점)가 서로 다른 수학적 근거에서 나온다는 걸 명확히 구분해서 설명할 수 있게 됨 — 인터�이서 "왜 i*i부터 시작하나요?"라는 질문에 바로 답변 가능한 수준.
