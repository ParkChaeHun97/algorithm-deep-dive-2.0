## 오픈채팅방 (2019 KAKAO BLIND RECRUITMENT)

### 문제
오픈채팅방 로그(Enter/Leave/Change, uid, 닉네임)가 주어질 때, 채팅방 입장/퇴장 메시지를 만들어 반환하는 문제. 핵심 함정은 한 유저가 닉네임을 변경하면, **그 이전에 있었던 입장 메시지에도 최종(가장 최근) 닉네임이 반영되어야 한다**는 점. 40분 만에 풀이 완료.

### 접근
- `map`(HashMap<uid, 닉네임>)으로 각 유저의 **최신 닉네임**만 계속 갱신(Enter든 Change든 공통으로 put)
- `uidAndMessage`(List<String[]>)에는 **"uid + 고정 메시지(들어왔습니다/나갔습니다)"만** 저장 — 이 시점에는 닉네임을 아직 끼워 넣지 않음
- 모든 로그를 다 처리한 뒤, 마지막에 `uidAndMessage`를 순회하며 각 uid에 대해 **그 시점의 최신 닉네임**을 `map`에서 조회해 최종 메시지를 조립
- `split.length`(3이면 Enter/Change, 2면 Leave)로 로그 종류를 구분

### 설계의 핵심
- "상태(현재 닉네임)"와 "이벤트 로그(무슨 일이 있었는지)"를 분리해서 관리하는 설계를 처음부터 적용함 — Enter를 만난 즉시 메시지를 완성해버리는 방식이 아니라, **메시지 조립을 맨 마지막까지 지연시키는(지연 바인딩) 구조**로 설계
- 이 분리 덕분에 Change 로그가 나중에 나와도 이미 만들어둔 메시지를 다시 찾아 고칠 필요 없이, 마지막 조회 시점에 자동으로 최신 닉네임이 반영됨
- 이 문제의 실제 난이도는 알고리즘보다 이 설계 포인트(상태와 이벤트의 분리)를 알아채는 데 있다는 것을 리뷰를 통해 확인함

### 리뷰 — 개선할 점
- 매직 스트링 하드코딩: `"Enter"`, `"님이 들어왔습니다."`, `"님이 나갔습니다."` 등이 코드 중간에 그대로 박혀 있음 — 상수로 추출하면 재사용/수정에 더 안전함
- `String[]`로 uid와 메시지를 묶어 저장하면서 `[0]`, `[1]`이 각각 무엇을 의미하는지 코드만 봐서는 알 수 없는 구조 — 다트 게임 리뷰 때도 나왔던 지적과 동일한 패턴. `record LogEntry(String uid, String message)`처럼 이름이 있는 구조로 바꾸면 `entry.uid()`, `entry.message()`로 의도가 명확해짐

### 효율성
- 전체 O(n) — record 배열을 두 번(맵 구성 1회, 결과 조립 1회) 순회, HashMap 조회도 평균 O(1)이라 효율적

## 회고
- 이번 문제는 로직 구현보다 "설계"가 핵심이었는데, 처음부터 상태와 이벤트를 분리하는 올바른 구조로 접근함 — 알고리즘 난이도와 별개로 문제의 핵심 함정을 정확히 짚어낸 사례
- "의미 없는 배열(String[]) 대신 이름 있는 구조(record/클래스)로 표현하기"라는 개선점이 다트 게임에 이어 이번에도 반복됨 — 이제 패턴으로 인식하고 다음 문제부터는 처음 설계 단계에서 바로 적용해볼 만한 시점
- 40분이라는 시간 안에 핵심 설계(지연 바인딩)를 막힘없이 구현한 것은, 그동안 여러 문제를 거치며 "문제가 요구하는 것의 본질을 먼저 파악하는" 습관이 쌓인 결과로 보임
