# 멀리 뛰기 (프로그래머스 Lv2, DP)

## 문제

한 번에 1칸 또는 2칸을 뛸 수 있을 때, n칸 끝에 도달하는 방법의 수를 1234567로 나눈 나머지를 구하기. n은 최대 2000.

## 접근

- 마지막 한 칸을 어떻게 밟았는지로 나누면, n칸에 가는 방법 = (n-1칸에 가는 방법) + (n-2칸에 가는 방법). 피보나치와 같은 점화식이고 dp 폴더의 11726(2xn 타일링)과 구조가 똑같음
- 배열 dp로 작은 n부터 채움. 초기값은 `dp[1]=1`, `dp[2]=2`, `dp[3]=3`, 더할 때마다 1234567로 나머지를 취함
- 처음엔 재귀 완전탐색(`+1`, `+2`로 갈라지는 방식)으로 풀었다가 시간초과가 나서 배열 dp로 전환

## 헷갈렸던 지점

- 재귀 로직은 맞았는데 왜 시간초과인지를 바로 못 짚었음. 매번 두 갈래로 갈라져서 호출 수가 2^n으로 늘고, 같은 depth를 여러 경로로 만날 때마다 그 아래를 처음부터 다시 계산하는 게 원인이었음
- 재귀에 저장 기능을 붙이는 쪽(메모이제이션)과 배열 dp로 바꾸는 쪽 중에 배열 dp를 골랐음

## 실수

1. 재귀 완전탐색은 로직은 맞지만 시간초과
    - `static int result`가 호출이 끝나도 값이 남아서, 채점이 같은 JVM에서 테스트케이스를 이어서 돌리면 이전 값이 누적될 위험이 있었음
    - `% 1234567`을 마지막에 한 번만 해서, 중간 값이 이미 int 범위를 넘을 수 있었음
2. `dp[i] = dp[i-1] + dp[i-2] % 1234567` — 자바에서 `%`가 `+`보다 우선순위가 높아서 `dp[i-1] + (dp[i-2] % 1234567)`로 읽힘. 나머지 연산이 합 전체가 아니라 `dp[i-2]`에만 걸렸음
    - 값이 1234567을 넘기 전(n=29까지)에는 나머지를 안 취해도 같은 값이라 버그가 가려졌고, n=30에서 처음 틀림 (내 코드 1346269, 정답 111702). n=2000에서는 1217977787 vs 694725
    - `(dp[i-1] + dp[i-2]) % 1234567`로 괄호를 묶어서 해결
3. `solution`이 호출될 때마다 항상 2000칸을 다 채움 — 결과엔 영향이 없지만 낭비. 배열 크기를 줄이려면 `dp[3]` 같은 초기값 대입이 n이 1, 2일 때 범위를 벗어나지 않는지 같이 봐야 함

## 회고

- 완전탐색이 시간초과일 때 "같은 부분 문제를 반복 계산하고 있다"를 알아채는 게 dp로 가는 첫 단계라는 걸 다시 확인함. 점화식은 2xn 타일링에서 이미 익혀둬서 방향을 잡자마자 바로 짰음
- 연산자 우선순위 때문에 `%`가 합 전체에 안 걸린 건, 플로이드-워셜 INF 오버플로우와 같은 계열의 실수임. 값이 커지는 연산에서는 나머지를 어디에 취하는지를 괄호까지 포함해서 확인해야 함
- 작은 n에서는 안 드러나고 큰 n에서만 터지는 버그라서 눈으로는 못 찾았고, 어느 n부터 틀리는지를 직접 돌려서 찾는 게 빨랐음
