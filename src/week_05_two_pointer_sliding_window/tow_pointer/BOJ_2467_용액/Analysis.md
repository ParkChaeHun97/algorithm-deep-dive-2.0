## BOJ_2467 - 용액

### 문제
- 오름차순 정렬된 N개의 정수(용액 특성값)에서, 두 개를 선택해 합이 **0에 가장 가까운** 조합을 찾는 문제
- 정답이 여러 개면 아무거나 출력

### 접근
- 양 끝에서 좁혀오는 투포인터 (지금까지의 1806/1644가 "한쪽으로만 진행하는" 투포인터였다면, 이번엔 "양쪽에서 안쪽으로 좁혀오는" 유형)
- `left=0, right=n-1`에서 시작
- 매 반복마다 `sum = arr[left] + arr[right]` 계산
    - **이동하기 전에** 먼저 현재 sum이 지금까지 최적값보다 0에 더 가까운지 비교/갱신
    - 그 다음 sum 부호로 이동 방향 결정: `sum < 0`이면 `left++`(값을 키워야 하니 작은 쪽 포인터를 전진), `sum > 0`이면 `right--`(값을 줄여야 하니 큰 쪽 포인터를 후퇴), `sum == 0`이면 더 좋을 수 없으니 즉시 종료

### 헷갈렸던 지점
1. **이동 방향 판단 기준**: sum이 음수면 왜 left를 옮겨야 하는지 헷갈림. 배열이 오름차순 정렬돼 있어서, left를 오른쪽으로 옮기면 더 큰 값을 만나 sum이 증가하고, right를 왼쪽으로 옮기면 더 작은 값을 만나 sum이 감소한다는 방향 감각을 재정리함.
2. **"이동 전 갱신" 순서 문제**: 처음엔 이동시킨 후에 비교하는 흐름으로 생각했는데, 이러면 이동하기 직전 상태(원래 더 가까웠을 수도 있는 조합)를 검사 없이 지나쳐버림. "매 반복에서 이동하기 전에 반드시 한 번씩 비교"하는 순서로 잡아야 모든 조합을 빠짐없이 검사할 수 있음을 확인.
3. **static 필드 vs 지역변수 스코프 오해**: 임시값(`water_1`, `water_2`, `result` 등)을 static 필드로 선언하면 "미리 선언해서 더 빠를 것"이라 생각했으나, Java에서 지역변수는 스택 슬롯 재사용이라 반복 선언 비용이 사실상 없고, static 필드는 오히려 클래스 메타데이터 접근 비용이 붙어 더 느릴 수 있음을 확인. 진짜 최적화 포인트는 "반복문 안 객체 생성"이나 "불필요한 반복 함수 호출" 같은 것이고, 단순 변수 선언 위치는 성능과 무관함.

### 코드 작성 중 발생했던 실수들
1. (설계 검토) 임시 변수들을 static 필드로 선언했다가, 근거 없는 성능 가정이었음을 확인하고 전부 지역변수로 리팩토링
2. 최적값 갱신과 포인터 이동의 순서를 처음엔 반대로 생각했다가 반례로 교정

### 회고
- 이번 문제로 "양 끝에서 좁혀오는" 투포인터와 "한쪽으로만 진행하는" 투포인터를 구분해서 체감함. 두 유형 모두 "정렬된 배열의 단조성을 이용해 탐색 범위를 절반씩 줄여나간다"는 공통점이 있다는 것도 확인.
- "갱신은 이동 전에, 이동은 갱신 후에" 라는 순서 원칙을 명확히 세움 — 슬라이딩 윈도우/투포인터 계열 문제에서 반복되는 실수 포인트였는데, 이번에 확실히 정리됨.
