## 카카오 2023 - 이모티콘 할인행사

### 문제
n명의 사용자와 m개(최대 7개)의 이모티콘이 주어짐. 각 이모티콘의 할인율은 10/20/30/40% 중
하나로 설정 가능. 각 사용자는 [기준비율, 기준가격]을 가지며, 기준비율 이상 할인하는
이모티콘을 모두 구매하되, 구매 총액이 기준가격 이상이면 구매를 전부 취소하고 플러스
서비스에 가입함(이 경우 구매액은 매출에서 완전히 제외). 모든 할인율 조합 중 1순위로
플러스 가입자 수를 최대화하고, 2순위로 매출액을 최대화하는 조합을 찾아 [가입자수, 매출액]을
반환하는 문제.

### 접근
- 이모티콘마다 4가지 할인율 중 하나를 배정하는 **중복 허용 완전탐색**(백트래킹) 사용.
  15649/15650과 달리 used 배열이나 start 파라미터가 필요 없는, 매 자리마다 독립적으로
  4가지 중 하나를 고르는 단순한 형태(4^m, m≤7이라 16384가지로 완전탐색 가능)
- 조합이 완성될 때마다 시뮬레이션 실행: 각 사용자에 대해 기준비율 이상인 이모티콘만 골라
  할인가 합산 → 합산액이 기준가격 이상이면 가입자+1(매출 미포함), 아니면 그 금액을
  매출에 더함
- 모든 조합의 시뮬레이션 결과 중 "1순위 가입자 수 최대, 2순위(동점시) 매출 최대"인
  조합을 최종 답으로 채택

### 헷갈렸던 지점
- **할인율(우리가 설정하는 값)과 사용자의 기준비율을 혼동**: 처음엔 users의 [40, 25] 같은
  값을 이모티콘 자체의 할인율로 착각함. 실제로는 "사용자가 요구하는 최소 할인율 기준"이고,
  이모티콘의 실제 할인율은 문제 푸는 쪽에서 결정해야 하는 값이라는 것을 재확인함
- **플러스 가입 시 매출 처리 방식**: 가입으로 전환된 사용자의 구매 비용이 매출에 포함되는지
  헷갈렸으나, "구매를 모두 취소하고 가입"이라는 조건 그대로 해당 금액이 매출에서 완전히
  빠진다는 것을 확인함

### 실수
- **1순위/2순위 비교 로직에서 `>=`로 뭉쳐 처리하는 버그**:
  ```java
  if(serve >= bestServe) {
      bestServe = serve;
      bestRevenue = totalRevenue;  // 가입자 수가 같아도 무조건 매출을 덮어써버림
      if(serve == bestServe){ ... } // 이미 위에서 덮어쓴 뒤라 이 블록이 무의미해짐
  }
  ```
  가입자 수가 같은 두 조합을 비교할 때, 매출이 더 낮은 조합이 나중에 나오면 그대로
  덮어써버려 이전의 더 나은 매출 값이 유실되는 문제. `>`(초과, 무조건 갱신)와
  `==`(동점, 매출 비교 후 갱신) 케이스를 `else if`로 명확히 분리해야 한다는 것을 확인:
  ```java
  if (serve > bestServe) {
      bestServe = serve;
      bestRevenue = totalRevenue;
  } else if (serve == bestServe && totalRevenue > bestRevenue) {
      bestRevenue = totalRevenue;
  }
  ```

  Lv2 중에서도 까다로운 축으로 평가받는 이 문제를 완전탐색+시뮬레이션+다중조건 비교까지
  스스로 설계해 완성함. 총 1시간 15분 소요, 그 중 마지막 다중조건 비교 버그를 고치는 데
  약 20분이 걸림

  향후 비슷한 다중 기준 최적화 문제(여러 정렬 기준이 있는 그리디 등)에서도 반복될 수 있는

  끝까지 정확히 짚어내고 완성까지 도달한 것은 이번 9주차에서 의미 있는 성과였음
