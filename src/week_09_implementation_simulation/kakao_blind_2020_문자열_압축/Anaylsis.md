## 카카오 2020 BLIND RECRUITMENT - 압축

### 문제
문자열 s가 주어질 때, 앞에서부터 일정 길이(step) 단위로 잘라나가면서 바로 직전 조각과 같으면 "반복횟수+조각" 형태로 압축한다. step은 1부터 s.length()/2까지 전부 시도해보고, 그중 압축 결과 길이가 가장 짧아지는 경우의 길이를 반환하는 문제. 문자열 끝에 나눠떨어지지 않고 남는 부분은 그대로 둔다.

### 접근
- step을 1부터 `s.length()-1`(사실상 `/2`까지만 의미 있음)까지 완전탐색
- 각 step마다 문자열을 `substring`으로 잘라 `List<String>`(cutString)에 저장
- 같은 조각이 연속되는 구간을 그룹으로 묶어 카운트(`count`)한 뒤, **그룹이 끝나는 시점에 한 번만** 길이를 누적:
    - 반복이 1번이면 조각 길이만 더함
    - 2번 이상이면 조각 길이 + 반복횟수를 나타내는 숫자의 자릿수를 더함 (`String.valueOf(count).length()`)
- 모든 step에 대해 계산한 길이 중 최솟값(`bestLength`)을 반환

### 실수
1. **반복 횟수를 세지 않고 "같은 게 나왔다/아니다"만 boolean으로 처리**: 처음 짠 코드는 같은 조각이 몇 번이든 무조건 `+1`만 하고 끝나서, 반복이 10번이든 100번이든 자릿수 증가를 전혀 반영하지 못함 (`"aaaaaaaaaaaaaaaaaaaa"` 같은 반례로 발견)
2. **자릿수 계산 시점의 카운트 값이 실제 반복횟수보다 1 작은 값을 기준으로 함**: `sameCount`를 "occurrences - 1"로 관리하면서 자릿수를 그 값으로 계산해, 반복횟수가 정확히 10/100/1000으로 넘어가는 경계에서 자릿수 증가가 한 번씩 누락됨
3. **그룹이 바뀔 때 카운트 리셋값을 0으로 잘못 설정**: 초기값은 `sameCount = 1`(현재 1번 나왔다는 의미)로 쓰면서, 새 그룹 시작 시에는 `sameCount = 0`으로 리셋해 카운트 체계가 어긋남 → `sameCount = 1`로 통일해서 해결
4. 위 실수들은 모두 "빼고 다시 더하는" 방식(자릿수 차이만큼 보정)으로 임시 처리하다 발생했고, 최종적으로는 "그룹이 끝나는 시점에 한 번에 계산"하는 구조로 바꾸며 자연스럽게 해소됨

### 토론한 내용
- 반복 횟수 경계(9→10, 99→100 등)에서 자릿수가 바뀐다는 점을 반례로 직접 확인하며 버그를 좁혀나감
- "중간에 값을 빼고 다시 더하는" 코드가 왜 가독성이 떨어지는지, 그리고 "그룹 종료 시점에 한 번만 계산"하는 패턴이 왜 더 명확한지 비교함 — 그룹핑 후 집계하는 유형의 문제에 일반적으로 적용 가능한 패턴이라는 것으로 정리
- 효율성 측면에서 O(n²)이 이 문제 제약조건(길이 1000 이하)에서는 충분하다는 것과, `substring` 호출이 매번 새 객체를 생성한다는 점(입력 크기상 무시 가능한 수준)을 짚음

## 회고
- 자릿수 경계처럼 "값이 특정 임계치를 넘을 때"가 반례의 핵심 포인트가 된다는 걸 다시 확인함 — 앞으로도 카운트/자릿수가 들어가는 문제는 9→10, 99→100 같은 경계값을 직접 테스트케이스로 만들어보는 습관이 필요
- 처음엔 "일단 통과되게" 임시방편(빼고 더하기)으로 고쳤다가, 이후 리뷰를 통해 더 근본적인 구조(그룹 종료 시점 집계)로 리팩터링하는 흐름을 경험함 — 통과 여부와 별개로 코드 구조 자체를 다시 보는 습관을 들일 필요 있음
