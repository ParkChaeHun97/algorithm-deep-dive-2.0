## 백준 1976 - 여행가자

### 문제
도시 N개와 인접행렬(N*N, 1이면 두 도시가 직접 연결)이 주어지고, 여행 계획에 포함된 M개의
도시가 전부 (직접 또는 간접적으로) 연결되어 있는지 확인하는 문제. 인접행렬을 union으로
전처리한 뒤, 계획 도시들이 모두 같은 대표를 가지는지 확인하는 유니온 파인드 문제.

### 접근
- N*N 인접행렬을 순회하며 `matrix[i][j]==1`인 쌍을 전부 union
- 여행 계획 도시 목록을 순서대로 읽으며, 첫 도시의 대표(find)를 기준으로
  나머지 도시들의 대표와 계속 비교
- 하나라도 대표가 다르면 즉시 NO 출력 후 종료, 끝까지 다 같으면 YES

### 헷갈렸던 지점 / 실수
- **parent 배열 초기화 누락**: 1717에서 겪었던 것과 같은 유형의 실수가 처음엔 아예 초기화 루프 자체가
  빠진 형태로 재발함 (`parent[i]=i` 루프 없이 바로 union 호출) → 추가해서 해결
- **인접행렬 파싱 범위를 N이 아닌 M으로 잘못 설정**: 인접행렬은 N*N인데 열 순회를 M번만 돌게 되어
  있어 행렬을 끝까지 못 읽는 문제 → `j <= N`으로 수정
- **charAt으로 공백 구분 문자열을 파싱하려던 실수**: "0 1 0" 형태 문자열을 charAt(j)로 직접 접근하면
  공백 때문에 인덱스가 밀림 → StringTokenizer로 토큰 단위 파싱하도록 수정
- **find(parent[number])로 불필요하게 한 단계 우회**: find(number)만으로 충분한데 parent[number]를
  먼저 넣어 혼동을 줌 → find(number)로 직접 호출하도록 수정
- **find 함수에 경로 압축 누락**: 어제 짠 경로 압축(`parent[a]=find(parent[a])`)이 처음엔 빠져있었음
  → 추가 (이 문제 규모(N≤200)에선 성능 영향 없지만 습관적으로 반영)
- **비교용 변수에 find 결과가 아닌 원본 번호를 대입하는 실수**: 여행 계획 도시들을 순회하며 이전
  도시의 "대표"를 저장해둬야 하는 변수(`find`)에 `nextFind`(find 결과)가 아니라
  `nextNumber`(원본 도시 번호)를 대입 → 다음 비교부터 잘못된 값과 비교하게 되는 버그
  → `find = nextFind;`로 수정

## 회고
- 1717에서 겪었던 실수(parent 초기화 누락)가 유사한 형태로 다시 발생함, 유니온 파인드 문제를
  풀 때 "초기화부터 확인"하는 걸 아예 체크리스트화할 필요가 있어 보임
- 오늘은 시간이 촉박한 상태에서 진행되어 실수가 평소보다 많았음. N/M 혼동, 파싱 방식,
  변수 대입 실수 등 기본기보다는 부주의에서 비롯된 문제들이 대부분이었음
- find/union 자체의 원리(대표를 찾아서 비교/연결)는 정확히 이해하고 있고, 왜 union에서
  양쪽 다 find를 거쳐야 하는지도 스스로 짚어낸 상태, 개념은 탄탄하나 실전 코드 작성 시
  시간 압박 속에서 꼼꼼함이 떨어지는 경향이 있음을 확인
