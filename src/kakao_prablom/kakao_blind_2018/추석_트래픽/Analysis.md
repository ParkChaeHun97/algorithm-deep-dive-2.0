## 추석 트래픽 (2018 KAKAO BLIND RECRUITMENT)

### 문제
초당 최대 처리량(임의의 시각부터 1초간 처리 중인 요청의 최대 개수)을 구하는 문제. 각 로그는 "응답완료시간 S"와 "처리시간 T"로 구성되며, 처리시간은 시작시간과 끝시간을 모두 포함한다(즉 실제 구간 길이는 T초이지만, 시작시각 계산 시 1ms 보정이 필요함). 응답완료시간은 항상 2016년 9월 15일로 고정, 로그는 응답완료시간 기준 오름차순 정렬되어 있음. N은 최대 2,000.

### 접근
- **시간 파싱**: `"2016-09-15 21:00:00.464 1.466s"`를 공백으로 분리 → 날짜/시간/처리시간 3파트로 나눈 뒤, 시간 파트는 `[:.]` 정규식으로 시/분/초/밀리초 분리, 처리시간 파트는 마지막 글자(`s`)만 `substring`으로 잘라내고 `Double.parseDouble()`로 통째로 파싱 → 모두 ms 단위 정수로 환산
- **시작 시각 계산**: `startTime = resTime - processTime + 1` — "시작과 끝을 모두 포함"하는 처리시간 정의 때문에 단순 뺄셈이 아니라 +1ms 보정이 필요함 (예제2로 직접 검증)
- **핵심 아이디어(브루트포스에서 최적화로 전환)**: 모든 밀리초를 순회하는 대신, 최대 처리량이 나오는 1초 구간의 "시작점"은 반드시 **어떤 요청의 시작 시각** 또는 **어떤 요청의 종료 시각(응답완료시간)** 중 하나와 일치한다는 성질을 이용 — 총 2N개의 후보 구간만 확인하면 충분 (O(N²))
- **겹침 판정**: 후보 구간 `[t, t+999]`와 요청 j가 겹치는 조건은 `(요청 j의 시작 ≤ t+999) AND (요청 j의 끝 ≥ t)` — 하나의 AND 조건으로 겹침 여부를 판정, 각 후보 구간마다 겹치는 요청 개수를 세어 그 최댓값을 최종 답으로 함

### 헷갈렸던 지점
- **날짜가 여러 날에 걸칠 가능성**: 문제 조건상 응답완료시간이 9월 15일로 고정된다는 걸 나중에야 확인함. 그 전까지는 자정을 넘어가는 경우(예: 23:59:59.900에서 처리시간을 빼면 전날로 넘어감)까지 고려해서 `LocalDateTime`/`ChronoUnit` 사용을 논의했으나, 결국 "하루 기준 ms로 환산 + 음수 허용"만으로 충분하다는 결론에 도달함 (날짜 자체는 파싱할 필요 없음)
- **정규식으로 처리시간을 분리하려던 시도**(`split("[.a-z]")`)가 처리시간의 자릿수가 가변적(`"2s"`, `"0.1s"`, `"0.351s"` 등)이라는 점에서 실패할 뻔함 — `substring`으로 `s`만 떼어내고 통째로 `parseDouble`하는 방식으로 전환하여 해결
- **"1초 윈도우"와 "요청 자체가 차지하는 구간"을 혼동**: 처음에 `calculateStartEndTimes`에서 `endTime = startTime + 999`로 모든 요청을 무조건 1초 폭으로 계산하려 했음 — 이는 "요청이 실제로 걸쳐있는 구간(길이=처리시간)"이 아니라 "시작 시각 기준 1초 윈도우"였다는 개념적 혼동. 논의 끝에 이 함수 자체가 불필요하다는 걸 깨닫고, `startTime`만 반환하는 함수로 단순화함

### 실수
1. **`lines[0]`, `lines[1]`을 for문 안에서 인덱스 `i` 대신 고정으로 참조** — 모든 반복에서 같은 줄만 처리하는 심각한 버그. `input = lines[i]`로 받아놓고 정작 안 쓰고 `lines[0]`을 계속 참조하는 실수도 반복됨
2. **`startTime = resTime - processTime - 1`로 부호를 반대로(-1)** — 예제2를 손으로 검증하며 `+1`이 맞다는 걸 확인
3. **겹침 판정을 두 개의 독립된 if문으로 나눠 각각 카운트** — `(시작 조건)`과 `(끝 조건)`을 AND로 묶어야 하는데 따로따로 `count++`를 해서 중복/오판정 발생 가능성이 있었음
4. **카운트 변수(`startCount`, `resStartCount`)를 안쪽 for문(j) 안에서 매번 0으로 재선언** — 누적이 전혀 안 되고 매번 최대 1까지밖에 못 세는 버그. 바깥 for문(i) 시작 직후로 위치를 옮겨 해결
5. **`result[i] = Math.max(...)`도 안쪽 루프 안에 있어서 마지막 j의 결과만 반영됨** — 안쪽 루프가 끝난 뒤로 위치 이동
6. **`nextResTime = msArray[j][1]`로 인덱스를 잘못 참조** — `[1]`은 처리시간이지 종료시각이 아님. 종료시각은 `msArray[j][0]`이어야 함
7. **`nextStartTime`을 `msArray[j][0]`(응답완료시간)에서 가져옴** — 이러면 `nextStartTime`과 `nextResTime`이 완전히 같은 값이 되어 시작/종료 구분이 무의미해짐. `startTimes[j]`(계산된 시작 시각 배열)에서 가져오도록 수정

### 토론한 내용
- 카카오 기출을 처음으로 "유형 힌트 없이 스스로 유추"하는 방식으로 시도함 — 도중에 어시스턴트가 실수로 유형을 먼저 언급해버려 완전한 무힌트 유추는 아니었지만, 이후 접근은 전적으로 스스로 설계함
- "브루트포스로 모든 밀리초를 순회하면 안 되는 이유"를 N(최대 2,000~3,000)과 전체 타임라인 길이를 곱해보며 직접 검증 → 대신 "최적 구간의 경계는 반드시 어떤 요청의 시작/종료 시각과 맞물린다"는 성질을 이용해 O(N²)로 축소하는 아이디어를 스스로 도출함
- 함수 설계를 여러 번 고쳐나가는 과정(처음엔 `[start, end]` 쌍을 반환 → 불필요함을 깨닫고 `start`만 반환하는 함수로 단순화)을 거치며, "이 메서드가 정확히 무엇을 계산해서 반환해야 하는가"를 매번 재정의하는 연습을 함

## 회고
- 이번 문제는 지금까지 푼 카카오 기출 중 가장 개념적으로 어려웠음 — 단순 구현이 아니라 "왜 모든 지점을 다 볼 필요 없이 2N개 후보만 보면 충분한가"라는 최적화 아이디어 자체를 스스로 도출해야 했던 첫 문제
- 실수 패턴이 이전 주(DP, 그래프, 유니온파인드)와는 다른 결이었음 — 이번엔 "인덱스 하나 잘못 참조"(`[0]` vs `[1]`), "변수 선언 위치"(루프 안/밖) 같은 사소해 보이는 디테일이 전체 로직을 완전히 무력화시키는 경우가 많았음. 반례를 만들기보다 정상 케이스를 손으로 천천히 따라가며 값이 이상해지는 지점을 찾는 방식이 더 유효했음
- 함수를 만들었다가 "이 함수가 왜 필요했는지" 스스로 되물으며 불필요한 함수(`calculateStartEndTimes`)를 걷어낸 과정이 인상적이었음 — 설계를 계속 고쳐나가는 것 자체가 이 문제를 푸는 데 필요한 사고 과정이었음
- 다음에 비슷한 유형(슬라이딩 윈도우/구간 겹침 판정)을 만나면, "후보 지점이 어디인지"부터 먼저 증명하듯 짚고 들어가는 습관을 가져가면 좋을 것 같음
