## 보석 쇼핑 (2019 KAKAO 개발자 겨울 인턴십)

### 문제
진열대에 순서대로 나열된 보석들(gems 배열)에서, **모든 종류의 보석을 적어도 하나씩 포함하는 최소 길이의 연속 구간**을 찾는 문제. 자는 동안 미리 "투포인터 + 해시"라는 유형을 스스로 떠올리고 다음 날 접근을 시작함.

### 접근 (최종 정답 구조)
- HashMap으로 현재 구간 `[left, right]` 안의 보석별 개수를 관리
- `right`를 0부터 끝까지 한 방향으로만 늘려가며, 매번 `count.size() == 전체 종류 수`(=모든 종류가 구간에 포함됨)를 확인
- 조건을 만족하는 동안 `while` 루프로 `left`를 계속 당기면서, **매 순간의 구간 길이를 계산해 지금까지의 최솟값과 비교/갱신**
- `left`를 당길 때 개수가 0이 되면 `count.remove()`로 완전히 제거 — "구간에 없음" 상태를 명확히 표현
- `right`가 끝까지 도달할 때까지 이 과정을 반복하여, 모든 가능한 후보 구간 중 최소 길이를 찾아냄

### 시행착오

**1차 시도 — 양 끝에서 안쪽으로 한 번씩 밀어 고정하는 방식**
- `right`를 배열 끝에 고정한 채 `left`를 오른쪽으로 밀어서 "어떤 보석이 0개 되기 직전"에 고정
- 그다음 그 `left`를 고정한 채 `right`를 왼쪽으로 당겨서 또 고정
- **반례 `[1,4,3,2,2,1]`로 실패**: 1단계에서 `right`를 배열 끝(인덱스6)으로 고정한 상태에서 계산을 시작하다 보니, 실제 최적 구간(`[1,4]`, 길이4)이 `right=4`에서 나오는데도 그 가능성 자체를 검토하지 못하고 `[2,6]`(길이5)라는 더 나쁜 답을 냄
- 문제의 본질: "오른쪽 끝을 하나로 고정해놓고 한 번만 계산"하면, 그 오른쪽 끝이 최적이 아닐 경우 정답을 영영 놓침 — 가능한 모든 오른쪽 끝 위치에서 나올 수 있는 후보를 전부 검토해야 한다는 걸 반례로 확인

**2차 시도 — HashMap 기반으로 개선했으나 여전히 결함 있음**
```java
if(!map.containsKey(gems[i])) {
    map.put(gems[i], 1);
    bestRight = i;
    while(map.get(gems[bestLeft]) > 1) {
        map.put(gems[bestLeft], map.get(gems[bestLeft]) - 1);
        bestLeft++;
    }
} else {
    map.put(gems[i], map.get(gems[i]) + 1);
}
```
- **반례 `[1,2,2,2,3,2,3,1,3]`로 실패** (정답 길이3인 `[6,8]`을 못 찾고 길이5를 반환)
- 결함 두 가지:
    1. `bestLeft`, `bestRight`를 갱신될 때마다 그냥 덮어쓰기만 하고, **여러 후보 구간의 길이를 비교해 최솟값을 기록하는 절차 자체가 없었음** — 마지막에 계산된 값이 곧 반환값이 되는 구조라, 중간에 더 짧은 후보가 나와도 놓침
    2. `while(map.get(...) > 1)` 조건 때문에 **개수가 정확히 1로 남으면 더 이상 줄이지 않음** — "그 보석이 구간에서 완전히 빠지는(0개가 되는) 지점"까지 당겨야 하는 경우를 처리 못 함. "1개 남음"과 "0개(완전히 없음)"을 구분하지 못한 게 근본 원인

### 토론한 내용
- 투포인터의 핵심 원칙을 반례를 통해 재확인: "오른쪽은 한 방향으로만 늘리고, 늘어날 때마다 조건을 만족하는 동안 왼쪽을 최대한 당기며 매번 후보를 기록/비교"해야 하며, 한 번의 시도로 답을 확정하려 하면 반드시 놓치는 케이스가 생김
- "매번 left를 체크해서 개수를 줄인다"는 사용자 표현으로 최종 정리됨 — right가 늘어날 때마다 조건을 확인하고, 만족하면 즉시 left를 당길 수 있는 만큼 당기는 것을 반복하는 구조
- 시간복잡도가 왜 O(n)인지도 짚음: right는 전체를 통틀어 한 번만 늘어나고, left도 전체를 통틀어 최대 n번만 이동(되돌아가지 않음)하므로 이중 루프처럼 보여도 실제로는 O(n)

## 회고
- 문제를 처음 본 순간(자기 전) "투포인터+해시"라는 유형을 스스로 정확히 짚어낸 것은 그동안 쌓인 유형 감각이 제대로 작동하고 있다는 신호였음. 다만 실제 구현 단계에서 "포인터를 어떻게 움직여야 모든 후보를 놓치지 않는지"에 대한 세부 원칙(오른쪽 단조 증가 + 매 순간 최솟값 비교)이 부족해 두 번의 시행착오를 거침
- 두 번의 실패 모두 "일부 케이스에서는 우연히 맞다"는 공통점이 있어 눈으로 코드만 봐서는 결함이 잘 안 보였고, 랜덤 테스트/반례 탐색으로 검증한 뒤에야 명확한 반례가 드러남 — 이번 주 내내 반복된 "직접 실행해서 검증하기" 패턴이 여기서도 결정적이었음
- 이번에 명확히 정리된 원칙(포인터는 한 방향으로만 이동 + 매 순간 후보 비교 + "완전히 0이 되는 상태"를 명시적으로 구분)은 투포인터/슬라이딩 윈도우 계열 문제 전반에 적용되는 일반 원칙이라, 다음에 비슷한 유형을 만날 때 바로 재사용할 수 있을 것 같음
