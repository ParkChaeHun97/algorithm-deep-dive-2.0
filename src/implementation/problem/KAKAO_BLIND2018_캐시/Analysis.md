## 카카오 2018 BLIND RECRUITMENT - 캐시

### 문제
캐시 크기(cacheSize)와 도시 이름 배열(cities)이 주어질 때, LRU(Least Recently Used)
캐시 교체 정책에 따라 각 도시 이름을 조회했을 때 걸리는 총 실행시간을 구하는 문제.
캐시에 있으면(hit) 실행시간 1, 없으면(miss) 실행시간 5이며, 캐시가 꽉 찬 상태에서 miss가
나면 가장 오랫동안 사용되지 않은 데이터를 제거하고 새 데이터를 넣는다. 도시 이름은
대소문자 구분 없이 같은 도시로 처리한다.

### 접근
- `List<String>`(LinkedList)로 캐시를 관리: 리스트 앞쪽=오래된 것, 뒤쪽=최근 사용
- 매 도시 이름을 조회할 때 리스트를 순회하며 동일 문자열(소문자 변환 후 비교) 존재 여부와
  인덱스(idx)를 먼저 찾음
- hit(idx != -1): 기존 위치에서 제거 후 리스트 맨 뒤로 재삽입, 실행시간 +1
- miss(idx == -1): cacheSize <= list.size()면 맨 앞(가장 오래된 것) 제거 후 맨 뒤에 추가,
  아니면 그냥 맨 뒤에 추가. 실행시간 +5
- cacheSize == 0인 경우는 별도 조기 리턴으로 처리: 캐시 공간이 없으므로 모든 접근이 miss이며
  `cities.length * 5`를 바로 반환

### 실수
- **LRU 개념 자체를 모르고 시작**: 사전 지식이 필요한 문제 유형이었음
- **제거 대상을 잘못 이해**: 처음에는 "가장 마지막에 들어간 애를 무조건 제거"로 오해함.
  실제로는 "가장 오래 사용되지 않은 애"를 제거해야 하며, hit이든 miss든 방금 쓰인 데이터는
  항상 맨 뒤(최근)로 옮겨야 한다는 점을 놓침
- **hit 처리 시 순서 갱신 누락**: 초기 코드는 hit일 때 실행시간만 올리고 리스트 순서는
  그대로 둠 — LRU의 핵심 로직이 빠진 상태였음
- **cacheSize == 0 예외 처리 누락**: 캐시 공간이 없는데도 `list.isEmpty()` 분기를 타면서
  데이터가 계속 쌓이는 버그. 경계값(0)을 별도로 짚지 않아 발생

### 토론한 내용
- 자료구조를 배열로 관리해야 하는지 List로 관리해야 하는지 논의함. 배열은 중간 원소를 빼서
  뒤로 옮기는 연산(hit 처리)이 인덱스 이동까지 필요해 번거로운 반면, List는 `remove(idx)` +
  `add(value)`만으로 순서 갱신이 끝나 이 문제에 더 적합하다는 것으로 정리
- 탐색 도중 리스트를 즉시 변형하는 방식(`for`문 안에서 바로 `remove`)의 위험성을 짚음 →
  인덱스만 먼저 찾아 저장(`idx`)하고, 실제 `remove`는 루프를 빠져나온 뒤에 하는 방식으로 분리

## 회고
- LRU처럼 사전 지식이 필요한 문제는 개념을 모르면 아예 접근이 안 된다는 걸 체감함
- cacheSize == 0처럼 자명해 보이는 엣지케이스를 가장 먼저 놓쳤음 — 앞으로도 항상
  "경계값(0, 최대 크기 등)"부터 먼저 점검하는 습관이 필요함을 확인
- 로직을 하나씩 리뷰받으며 고쳐나가는 과정에서, hit/miss 각각의 순서 갱신 조건을 명확히
  구분해서 짜는 감각을 잡음
